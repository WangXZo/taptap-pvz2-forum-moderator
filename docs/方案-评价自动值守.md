# 方案：游戏评价（review）自动值守

> **状态：待大哥确认，未实施。**
> 2026-11-13 已完成 **A 级（能力入库）**：四个接口方法 + 手册 + 单测（74 条），全绿。
> 本文件是 **C 级（接入自动值守）** 的设计方案 —— 先把难点摊开、把要定的规矩列出来，
> 确认后再动手。**本轮不改任何运行逻辑。**

---

## 1. 目标

让 PVZ2 的**游戏评价**（差评为主）也进版主的自动化流程：
发现「值得回」的评价 → 按答疑库/上下文生成回复 → 回上去 → 校验落库 → 出报表。

## 2. 现状（A 级已完成）

| 已有 | 位置 |
|---|---|
| 拉评价列表 | `api.reviewList({appId, limit, sort})` |
| 回一条评价 | `api.reviewReply({reviewId, text, signature})` |
| 读全量回复 | `api.reviewComments({reviewId, limit, from, order})` |
| 校验落库 | `api.hasReviewReplyText({reviewId, text})` |
| 纯函数层（参数规范化 / 摊平 / 载荷） | `scripts/lib/review.mjs` |
| 实测手册 | `references/review-api.md` |
| 单测 | `scripts/test-review-api.mjs`（74 条断言） |

**验证方式**：全程只读 + **无损读回**（读大哥手动发过的那条确认端点正确），没有额外发过任何回复。

## 3. 评价 ≠ 帖子：六个结构性差异（**这是难点的全部**）

论坛那套（答疑库 → 三层上下文 → LLM → 回复 → 校验）**不能照搬**，因为：

| # | 差异 | 影响 |
|---|---|---|
| 1 | **评价没有标题、没有分栏正文**，只有一段短文本（`contents.text`） | `question-detect` 的判定规则是「标题+正文」，评价只有一段文字 → 判定规则要另写一套 |
| 2 | **评价只有一层回复**（实测 by-review 返回的 comment 里没有 `child_posts`） | 论坛的「楼中楼」通道、**互动续聊**在评价上用不了 → 玩家回我们之后，我们接不上话 |
| 3 | **评价数量远大于帖子**（`total = 10000`，且持续增长） | 不能「都扫一遍」；必须有窗口/增量游标，否则一轮就几百条 |
| 4 | **`contents` 是纯文本**，不支持 `tap_emoji` | 论坛的「自动配表情」在评价上**失效** → 文案要写成不带表情的样子 |
| 5 | **评价是「打分 + 短文本」，不是「提问」** | 「它想问什么」要靠语义判断，不是靠疑问词；差评里大量是**陈述**（"我的号又丢了，还老是闪退"） |
| 6 | **评价没有「楼主」概念**，回复者与评价者不是同一人 | 论坛的「楼主回复我 → 接话」模型在这里不成立 |

## 4. 采集设计（新增 watch 源 `review`）

```
watch 每轮 → 拉 GET /review/v2/list-by-app?app_id&limit=10&sort=new
           → 归一化成队列项 { reviewId, score, text, authorId, publishTime }
           → 按 score / 时间过滤
```

要定的：

| 开关 | 建议 | 说明 |
|---|---|---|
| `review.enabled` | 默认 **false** | 灰度用；能力已入库但**不自动跑** |
| `review.minScore` / `maxScore` | 只回 **1~3 星** | 4~5 星好评默认不回（回好评容易变刷屏） |
| `review.windowMinutes` | 只看**最近 N 分钟**的新评价 | 评价流是无限滚动，没有窗口就会越积越多 |
| `review.maxPerRun` | **1~2 条/轮** | 差评比帖子敏感，回复量必须更保守 |
| `review.everySeconds` | 跟其它源**错峰**（如 300s） | 少打接口，避 WAF |

> ⚠️ `sort=new` 是「最新在前」，评价流滚动很快 → 靠**时间窗口**而不是靠分页翻历史
> （分页翻 10000 条不现实，也没必要）。

## 5. 判定设计（要新写的一套）

论坛的判定链：**是不是提问 → 答疑库命中 → 敏感拦截 → LLM 生成**。
评价这边要改成：

```
差评文本 → ① 敏感拦截（退款/封号/充值/投诉/外挂/账号交易）
        → ② 归类：①账号/登录问题 ②BUG/闪退 ③玩法/难度 ④氪金/资源 ⑤吐槽 ⑥其它
        → ③ 能否用答疑库答？命中且置信度够 → 生成回复；命中不了 → 转人工
        → ④ 情绪安抚（纯吐槽/崩溃）→ 陪一句
```

**要定的**：

| 问题 | 说明 |
|---|---|
| **只回差评还是全回？** | 好评回不回？好评回「谢谢支持」= 刷屏 |
| **哪些差评不碰？** | 建议黑名单：涉及**退款/充值/封号/实名/账号被盗/未成年代理/投诉** → 礼貌说明帮不上，不表态 |
| **能不能用答疑库？** | 评价文本短且常是**陈述句**，关键词命中率天然低 → 阈值可能要另设（论坛 0.65，评价建议更高，否则乱答） |
| **回复长度** | 论坛 ≤1000 字符；评价回复建议**更短**（≤100 字符）—— 评价场景越短越自然，也降低说错话的风险 |
| **带不带表情？** | 评价接口没验证表情节点 → **不带**（纯文本） |
| **带不带签名？** | 带（跟其它出口一致，`clampReply` 统一加） |

## 6. 去重与状态

**独立文件** `data/review-state.json` —— 理由跟 `watch-queue.json` 一样：
守护循环和 `collect.mjs` 各持一份 state 会互相覆盖（历史踩过的坑）。

| 记什么 | 为什么 |
|---|---|
| `reviews[id].replied` | 已回过，别再回 |
| `reviews[id].stage` | `replied` / `no_need` / `manual` |
| `reviews[id].contentHash` | 内容指纹，防「同一段话重复回」 |

> 论坛那边有 `post_event` 事件流水做**持久凭据**（state 只是热缓存）。
> 评价要不要也上事件流水（SQLite）→ **看 C 级做多大**：
> - 轻量版：只 `review-state.json`（够用，评价量比帖子小）
> - 完整版：加 `review_event` 表（跟论坛一致，状态丢了也能恢复）

## 7. 校验落库

跟论坛一样「发完读回校验」，但**读的是 `by-review`**（列表里的 `review_comments` 是预览子集，不能信）：

```
reviewReply() → hasReviewReplyText({reviewId, text})
             → found=false → 记 manual（不重发，避免重复）
```

## 8. 报表

新增一类标记，跟论坛的四类并列：

| 标记 | 含义 |
|---|---|
| 🐟 已回复（评价） | 我们回过了 |
| ⏳ 待回复（评价） | 该回还没回 |
| 🖐 需人工（评价） | 回不了（敏感/答疑库没命中/校验失败） |
| ⚪ 无需回复（评价） | 好评/纯吐槽/重复内容 |

**建议单独出一份** `reports/review-<日期>.md`，别混进论坛报表 —— 两套内容、两种口径，混在一起看不清。

## 9. 灰度与回退

1. **第一步**：`review.enabled=false`（默认），只留能力 + 手动 CLI
2. **第二步**：开采集，**不回复**（`--no-reply`）→ 看它到底捞出什么、判得准不准
3. **第三步**：开回复，**每天最多 1 条**（`maxPerRun=1`），连续观察 3 天
4. **第四步**：放宽到 1~2 条/轮、窗口放宽

**回退**：把 `review.enabled` 改回 false 立刻停（不影响论坛链路）。

## 10. 实施步骤（确认后按这个顺序做）

| 步 | 交付 | 验收 |
|---|---|---|
| 1 | `scripts/review.mjs` 手动 CLI（列/回/校验） | 能手动回一条并校验到 |
| 2 | `lib/review-classify.mjs` 判定（归类 + 敏感拦截 + 答疑库匹配） | 单测：真实差评样本判对类别 |
| 3 | watch 新增 `review` 源（**先只采集不回**） | 一轮跑完出「捞到什么」的清单 |
| 4 | 回复链路 + 去重 + 校验落库 | 回一条 → 读回确认 |
| 5 | 报表 | 出独立评价报表 |
| 6 | 灰度调参 | 3 天观察后定参数 |

## 11. 待大哥确认的点（**动手前先定这些**）

1. **只回差评（1~3 星）还是全回？** 好评要不要回应？
2. **回多久以前的评价？**（建议：只看最近 30 分钟~2 小时的新评价）
3. **每轮最多回几条？**（建议 1 条起步）
4. **差评的敏感边界**（退款/充值/封号/账号盗）→ 建议一律「礼貌说明帮不上」，不表态。这个口径认可吗？
5. **答疑库在评价场景能不能用？**（建议：能用，但阈值比论坛**高**，命中不了宁可转人工）
6. **回复长度上限**（建议 ≤100 字符，比论坛短）
7. **要不要表情？**（建议不要 —— 评价接口未验证）
8. **报表独立出还是并进论坛报表？**（建议独立出）
9. **轻量状态还是上事件流水？**（建议先轻量）

## 12. 风险清单

| 风险 | 后果 | 对策 |
|---|---|---|
| 评价是**差评**，玩家情绪本来就冲 | 回复不当会**二次激怒** | 语气护栏 + 敏感拦截 + 拿不准就转人工 |
| 短陈述句被误判成提问 | 乱答、说错游戏数据 | 阈值调高 + 事实只来自答疑库 |
| 评价接口参数踩坑（如 `order`/`limit`） | 整条链路 400 | 参数规范化已做 + 单测锁住 |
| 刷屏 | 玩家反感 | `maxPerRun` 小 + 场景级负反馈（可复用现有 `sceneFeedback`） |
| 评价没有楼中楼 | 玩家回了我们接不上 | 明确告知：评价场景**只回一次**，不回不续聊 |
