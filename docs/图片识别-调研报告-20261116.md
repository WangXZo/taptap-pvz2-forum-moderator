# PVZ2 论坛图片识别调研报告

> 日期：2026-11-16 ｜ 性质：**调研 + 各路线实现方案**（先不动手实现）
> ⚠️ **2026-11-24：实现已拆成独立能力包 `image-recognition-ai-ocr`**。本文是**历史调研报告**，
> 现状与运维看 [../references/image-recognition.md](../references/image-recognition.md)。
> 目标：论坛大量帖子带图，当前图片识别能力为零；调研网络/GitHub 可用方案，给出**各路线实现方案**，并专项覆盖**适合 PVZ2 游戏画面特征识别**的路线。
> 结论速览：**带门控的分场景混合流水线**（大哥 2026-11-16 拍板，详见 §5）——①好友码/天宫码意图**跳过图片识别**；②其他帖先判图片相关性，无关配图跳过、相关图才识别；③识别内容并入帖子内容，进**网络搜索 + LLM 上下文**（两者现有流水线已具备）。识别手段：文字/码用本地 RapidOCR（免费即装），游戏画面/开放语义用云端 VLM（qianwen-vision 已配置）+ 本地模板匹配（**部分特征存 skill 资产库**），YOLO 仅批量植物检测时再上。

## 0. 现状与痛点（代码证据）

**skill 目前完全没有图片识别**，图片是已知盲区：

| 证据 | 位置 | 说明 |
|---|---|---|
| 图片帖被标「码在图里，文本提取不到」「未取到」 | `scripts/removed-list.mjs` L329/L347 | 好友码在截图里时，**取不到码**，只能标注放弃 |
| `isImage` 判定已存在 | `removed-list.mjs` L142 `!title && !summary && !contents.json` | 能识别「这是图片帖」，但**无法读图** |
| 富文本只抽文本、丢图 | `scripts/lib/http.mjs` L204-215 `flattenContents` 只收 `node.text` | **图片 URL 就在 `contents.json` 里，但被完全丢弃** |
| QA 匹配纯文本 | `collect.mjs` / `lib/compose-reply.mjs` | 带图求助帖（正文少、信息在图里）匹配不到答疑库 |

**三类痛点**：
1. **好友码 / 天宫码截图**：码在图里 → 撮合/回复拿不到码（最直接的业务损失）。
2. **求助游戏截图**：错误弹窗、闪退、卡关、植物阵容、关卡进度、**活动页面（活动植物/奖励/参与条件）**、**植物图鉴（植物图标/名称/说明文本/技能）**在图里 → 看不懂问题，答非所问或漏答。
3. **游戏画面特征**：植物种类、阳光数、关卡/UI 状态、僵尸类型 → 需要「看懂游戏画面」才能精准答疑。

**关键架构约束**：守护进程（`watch.mjs`）是 **headless Node 进程**，不能调用「agent（我）」的多模态能力。所以**全自动**路线必须走程序化接口（本地 OCR / 云端 VLM API）；「agent-in-loop」是半自动（守护标记 → 会话里由我读图）。

## 1. 论坛图片类型 × 识别需求矩阵

| 图片类型 | 典型内容 | 需要的能力 | 难度 |
|---|---|---|---|
| 好友码 / 天宫码截图 | 一串数字/字母码（可能带游戏背景） | **数字/字符 OCR** | 低（ROI 裁剪后很规整） |
| 错误弹窗 / 闪退截图 | 中文错误文案、错误码 | **中文 OCR** + 少量语义 | 低-中 |
| 卡关 / 关卡进度截图 | 关卡号、星级、进度条、植物阵容 | OCR + **游戏 UI 理解** | 中 |
| 植物阵容 / 晒卡截图 | 多个植物图标、等级、品质边框 | **目标检测/图标识别** + 语义 | 中-高 |
| **活动页面** ★重点 | 活动植物、奖励物品、参与条件/进度、活动规则文本 | **图标识别 + 中文 OCR + 语义** | 中-高 |
| **植物图鉴** ★重点 | 植物图标/名称、属性数值、技能/说明文本 | **图标识别 + 中文 OCR（说明文本）+ 语义** | 中-高 |
| 求助混合截图 | 游戏画面 + 玩家标注文字 | **多模态语义理解** | 高 |
| 评价配图 | 任意（晒图/吐槽图） | 语义理解（可选） | 中 |

> 启示：**不同图片用不同方法**，不存在「一个模型通吃且都最优」。码类用 OCR 最划算，开放理解用 VLM，固定 UI 用模板匹配。

## 2. 技术路线总览（6 条）

### 路线 A：本地传统 OCR（文字/数字提取）

- **原理**：检测文本框 → 识别字符，输出纯文本。不理解语义。
- **代表方案**：
  - **RapidOCR**（[rapidai/rapidocr](https://github.com/rapidai/rapidocr)）：PaddleOCR 模型转 ONNX，`pip install rapidocr onnxruntime`，whl ~15M 自带 3 模型（检测/方向/识别），中文综合评分第一、速度最快、支持旋转/低对比度。**本机已有 onnxruntime 1.19.2 → 装上即用**。
  - **PaddleOCR**（[PaddlePaddle/PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR)）：百度，轻量 <10MB，80+ 语言，中文准确率高，可自定义训练。本机有 paddlepaddle 2.4.2 框架但**未装 paddleocr 包**。
  - **ddddocr**（本机已装 1.5.6）：主打验证码/数字，**中文失败率 >90%**，形近字符（0/O、1/l/I、5/S）易混，需预处理。只适合干净数字码。
  - **Tesseract**：老牌，中文需额外语言包，准确率一般，本机未装二进制。
  - **EasyOCR**：安装最简但中文一般、复杂排版易错。
- **精度**：印刷中文 RapidOCR/PaddleOCR 高（手写 F≈75%）；干净数字码接近 100%；游戏艺术字/低对比度需预处理。
- **速度**：CPU 几十~几百 ms/图（RapidOCR mobile 最快）。
- **成本**：**完全免费、离线**。
- **本机就绪度**：★★★★★（onnxruntime/opencv/Pillow 都在，RapidOCR 一行 pip）。
- **适用**：好友码/天宫码、错误弹窗文字、关卡号等**规整文字**。
- **缺点**：不懂语义（不知道「这是豌豆射手」），艺术字/复杂背景需 ROI 裁剪+增强。
- **来源**：[RapidOCR 模型对比](https://raw.githubusercontent.com/RapidAI/RapidOCRDocs/refs/heads/main/docs/blog/posts/about_model/model_summary.md)、[RapidOCR 安装文档](https://rapidai.github.io/RapidOCRDocs/v3.8.0/install_usage/rapidocr/install/)、[中文 OCR 评测排名](https://blog.csdn.net/weixin_44714085/article/details/146980899)、[ddddocr 局限](https://ask.csdn.net/questions/9468675)。

### 路线 B：云端多模态 VLM（理解 + OCR）

- **原理**：视觉语言大模型，看图直接输出语义描述/结构化答案，能识别植物、读懂错误、理解阵容。
- **代表方案**：
  - **Qwen-VL**（`qianwen-vision` 技能 / DashScope）：Qwen3-VL OCRBench 8B≈97、30B-A3B≈95，显著强于 Qwen2.5-VL；能读游戏 UI（等级/金币/技能冷却/小地图/装备）并生成操作指引。
  - **doubao-vision**（`arkcli-understand` / 火山 ARK）：图片描述/OCR/视觉定位 bbox/GUI 识别，12 个任务型 sub-skill。
  - **百炼 vision**（`bailian-gen` 的 `bl vision describe` / `bl omni`）。
  - **MiniMax**（`mmx-cli`）。
- **精度**：开放语义理解最强；OCR 也强（Qwen3-VL）；游戏截图理解有实证（[Qwen2.5-VL 游戏界面](https://blog.csdn.net/weixin_42327217/article/details/156550691)、[Qwen3-VL UI](https://blog.csdn.net/weixin_42437253/article/details/158943351)）。
- **速度**：1~5s/图（网络+推理），论坛非实时场景完全够。
- **成本**：**按图计费**，量级约几分钱/图（精确单价用 `arkcli-pricing` / `qianwen-usage` 查；千问 Token Plan 剩余 53%）。
- **本机就绪度**：★★★★（qianwen/bl/mmx CLI 已装，凭据/额度需确认；ark 命令名待确认）。
- **适用**：求助截图理解、植物/阵容识别、错误语义、评价配图——**开放场景首选**。
- **缺点**：要联网、按量计费、**玩家截图上传第三方有隐私考量**；极小数字码偶尔不如专用 OCR 稳。
- **来源**：[Qwen3-VL OCR 基准](https://huggingface.co/datasets/VirtualLUO/Chronicles-OCR)、[CaptionQA 对比](https://arxiv.org/html/2511.21025v1)、[VLM 游戏 UI 实测](https://qiita.com/y4o4/items/051e0fb8552272723943)。

### 路线 C：本地端侧 VLM（离线理解）

- **原理**：把小型 VLM 跑在本机，离线看图理解。
- **代表方案**：
  - **ollama 拉视觉模型**：本机 ollama 在，但**当前无视觉模型**（只有 bge-m3/nomic-embed-text/qwen2.5-coder:7b）。可拉 `qwen2.5-vl:7b` / `minicpm-v` / `llava`。
  - **MiniCPM-V 4.7**（[OpenBMB](https://openbmb.cn/model/minicpm-v-4-7)）：1B OCRBench 86.1、35B-A3B OCRBench 91.2，端侧 ~3G 内存可跑，中文强。
  - **GOT-OCR2.0**（[stepfun-ai/GOT-OCR-2.0-hf](https://huggingface.co/stepfun-ai/GOT-OCR-2.0-hf)）：580M 端到端统一 OCR，消费级 GPU 可跑，擅长文档/公式/表格/场景文本，**偏结构化 OCR 而非游戏语义**。
- **精度**：中小模型 OCR/理解接近云端小模型，但复杂游戏语义弱于云端大模型。
- **速度**：取决于硬件（本机无独显信息，CPU 跑 7B VLM 偏慢，数秒~数十秒/图）。
- **成本**：免费离线，但**吃内存/算力**，需下载模型（数 GB）。
- **本机就绪度**：★★★（ollama 在，需拉模型 + 评估硬件）。
- **适用**：隐私敏感、离线、批量且不想付费的场景。
- **缺点**：硬件门槛、精度上限低于云端旗舰、部署维护成本。

### 路线 D：游戏专用 CV（模板匹配 / 找色 / YOLO）★游戏画面特征专项

- **原理**：传统 CV + 轻量检测，针对**固定游戏 UI/图标**做精确识别。
- **参考架构（权威）**：[BetterGenshinImpact](https://github.com/babalae/better-genshin-impact) 的 [CV 流水线](https://deepwiki.com/babalae/better-genshin-impact/4.1-computer-vision-pipeline)——`RecognitionObject` 统一抽象，分层识别：

  | 识别类型 | 方法 | 用途 |
  |---|---|---|
  | `TemplateMatch` | OpenCV `Cv2.MatchTemplate`（单/多目标+NMS，可 mask） | UI 按钮、图标、固定图案 |
  | `Ocr` / `OcrMatch` | PaddleOCR Det+Rec（ONNX）/ Yap SVTR | 读区域文字 / 找特定文字 |
  | `ColorMatch` | 颜色阈值 | 血条、元素颜色 |
  | `ColorRangeAndOcr` | 先滤色再 OCR | 高亮/地图文字 |
  | YOLO 检测 | ONNX 模型（BgiWorld 通用 / BgiAvatarSide 头像分类 / BgiQClassify） | 多物体检测/分类 |

- **PVZ2 实证（关键）**：
  - [Xiao-yu-ze/XYZ](https://github.com/Xiao-yu-ze/XYZ)：PVZ2 安卓自动化，「看图→判断→操作」用 **OpenCV 模板/找色/找字**——证明 PVZ2 画面可用传统 CV 识别。
  - 安静小精灵 PVZ2「自动点太阳」脚本：**区域找图 + 相似度 0.9**（找不到降到 0.8/0.7）——PVZ2 阳光/图标用模板匹配是社区成熟做法。
- **精度**：固定 UI/图标模板匹配可达 95%+（相似度阈值可调）；YOLO 多植物检测需标注训练。
- **速度**：模板匹配 ms 级，极快；YOLO ONNX CPU 几十 ms。
- **成本**：免费；**YOLO 需采集截图+标注（LabelImg/CVAT/Roboflow）+训练**，人力成本高。
- **本机就绪度**：★★★★（opencv 4.5.4 已装，模板匹配/找色**现在就能写**；YOLO 需 ultralytics+训练）。
- **适用**：**固定游戏画面特征**——植物图标、阳光数、关卡按钮、品质边框、错误弹窗模板。
- **缺点**：模板匹配只认「见过的图案」，新植物/新 UI 要补模板；分辨率/缩放敏感（需多尺度）；开放语义不行。
- **来源**：[BetterGenshinImpact CV](https://deepwiki.com/babalae/better-genshin-impact/4.1-computer-vision-pipeline)、[XYZ PVZ2](https://github.com/Xiao-yu-ze/XYZ)、[游戏 bot CV 实践](https://litres.com/book/uchitel-nachal-noi-34041113/programmy-dlia-prokhozhdeniia-komp-iuternykh-igr-boty-i-74457794/read/)。

### 路线 E：Agent-in-the-loop（半自动，零新增成本）

- **原理**：守护检测到图片帖 → 标记入「待看图」队列 → 在会话里由 agent（我）用 `read_image` 读图理解 → 回写 QA/答案/分类。
- **代表方案**：复用宿主多模态（`read_image`）+ 现有守护队列机制。
- **精度**：宿主大模型理解力强（等同云端旗舰 VLM）。
- **速度**：依赖会话在线，非 7×24 全自动。
- **成本**：**零新增 API 成本**（用现有会话额度）。
- **本机就绪度**：★★★★★（read_image + 守护队列都在）。
- **适用**：低频、高价值、需判断的图片帖；过渡期兜底。
- **缺点**：**不是全自动**（要会话介入），守护 headless 时无法自调用。

### 路线 F：第三方 OCR API（百度/腾讯/阿里）

- **原理**：云厂商通用/专用 OCR API。
- **精度**：中文印刷体高，有手写/表格/卡证专用模型。
- **成本**：按次计费（有免费额度），需开通+密钥。
- **本机就绪度**：★★（需要新开通账号/密钥）。
- **适用**：不想自建、要稳定 SLA 的场景。
- **缺点**：与路线 B 重叠但**只 OCR 不理解**，性价比不如直接用 VLM；新增账号管理成本。**一般不优先**。

## 3. 游戏画面特征识别专项（大哥重点）

**PVZ2 画面特征 → 最优方法映射**：

| 画面特征 | 推荐方法 | 理由 |
|---|---|---|
| 阳光数量 / 关卡号 / 进度数字 | **ROI 裁剪 + RapidOCR**（或专用数字分类器） | 数字规整，OCR 最稳最快；游戏字体可训练小分类器更准 |
| 植物图标（单个/已知） | **OpenCV 模板匹配**（多尺度+相似度阈值） | PVZ2 社区已验证（XYZ/安静小精灵）；图标固定 |
| 植物阵容（多植物格子） | 模板匹配批量（NMS）或 **YOLO 检测** | 格子布局固定→模板匹配够用；植物种类极多→YOLO |
| 品质边框 / 等级角标 | **ColorMatch + 模板匹配** | 颜色/图案固定 |
| 错误弹窗 / 闪退文案 | **RapidOCR 中文** + VLM 语义 | 先 OCR 取文案，VLM 判断错误类型 |
| 僵尸类型 / 开放画面理解 | **云端 VLM**（Qwen-VL） | 开放语义，模板匹配覆盖不了 |
| 「这关怎么过」综合求助 | **VLM 理解** + 模板匹配辅助 | 需要语义 + 画面结构 |

**分层架构（借鉴 BetterGenshinImpact）**：
```
截图 → 预处理(缩放/ROI/增强)
        ├─ 模板匹配层：已知 UI/植物图标/按钮（快、准、免费）
        ├─ OCR 层：数字/文字（RapidOCR）
        ├─ 颜色层：血条/品质边框
        └─ VLM 层：开放语义兜底（云端/本地）
        → 结构化结果 {植物:[...], 阳光:N, 关卡:X, 错误:"...", 语义:"..."}
        → 喂给 QA 匹配 / 分类 / 答疑
```
> 核心思想：**能用模板匹配/OCR 解决的不上 VLM，VLM 只做开放语义兜底**——省钱、快、可解释。YOLO 是「植物种类极多且需批量检测」时才上的重武器，**初期不建议**（标注训练成本高）。

## 5. 定稿设计与实现排期（大哥 2026-11-16 拍板）

**决策**：P0+P1 一起排期，做成一条**带门控的图片处理流水线**；**部分游戏画面特征保存到本地 skill**。

**三条规则**：
1. **好友码/天宫码意图 → 直接跳过图片识别**（走原有固定提醒+移出/撮合流程，不读图）。〔修正：原「P0 OCR 取码」取消——码帖按意图处理即可，不需要从图里读码〕
2. **其他意图 → 先判图片相关性**：无关配图（装饰/表情/无关晒图）跳过；相关图片才识别。
3. **相关图片识别出的内容 → 并入帖子内容 → 进入网络搜索 + LLM 上下文**。

**流水线**：
```
带图帖
 ├─ 意图=好友码/天宫码 ───────────────→ 跳过图片识别（原流程）
 └─ 其他意图
      ├─ 图片相关性门控
      │    ├─ 无关配图 ───────────────→ 跳过
      │    └─ 相关图片 ───────────────→ 识别
      │         ├─ 文字/错误文案/数字 → RapidOCR（本地免费）
      │         └─ 游戏画面/开放语义 → VLM（云端）或 模板匹配（本地特征库）
      └─ 识别内容 → post.text / post.imageText
            ├─ QA 匹配查询词增强（qa-vector + 关键词）
            ├─ 网络搜索查询词增强（lib/websearch.mjs，已有）
            └─ LLM 组答上下文（compose-reply.mjs，已有）
```

**与现有流水线的挂钩（都已存在，改动小）**：

| 现有能力 | 位置 | 图片内容如何接入 |
|---|---|---|
| 富文本抽文本 | `http.mjs` `extractText`/`flattenContents` | 新增 `extractImages` 取图 URL；识别文本并入 `text` |
| 意图分类 | `collect.mjs`（question/code/…） | 码意图 → 跳过图片识别（规则1） |
| QA 匹配 | `qa-vector.mjs` + 关键词 | `post.text` 增强后匹配更准 |
| 联网补答 | `lib/websearch.mjs`（baidu-websearch，单轮≤2次、同帖24h不重搜） | 查询词 `q` 用「正文+识别内容」拼 |
| LLM 组答 | `compose-reply.mjs`（QA资料+webNote+三层上下文） | 识别内容进 `topicForMatch`/上下文，LLM 看得到图里信息 |

> 关键：规则3 **不需要新建搜索/LLM 通道**——现有 `websearch` + `composeReply` 已具备，只要把识别内容灌进 `post.text`，三处（QA匹配/搜索词/组答上下文）自动受益。

**排期（P0+P1 合并为一条流水线，分步落地）**：

| 步 | 任务 | 路线 | 集成点 | 工作量 | 成本 |
|---|---|---|---|---|---|
| **S1** | 取图 + 意图门控 | — | `http.mjs` `extractImages`；`collect.mjs` 码意图跳过 | 小 | 免费 |
| **S2** | 图片相关性分类 | B 轻量VLM / 启发式 | 无关配图跳过，相关图才进识别 | 小-中 | 极低 |
| **S3** | 相关图识别（文字/错误/数字） | A RapidOCR | `pip install rapidocr`；ROI+增强+识别 | 小 | 免费 |
| **S4** | 相关图识别（游戏画面/语义） | B VLM（qianwen-vision） | 结构化描述（错误类型/植物/关卡/诉求） | 中 | 几分/图 |
| **S5** | 识别内容回灌流水线 | — | `post.text` → QA匹配 / websearch / composeReply | 小 | 免费 |
| **S6** | 游戏特征模板库（本地 skill） | D 模板匹配 | `assets/game-features/` 模板图+特征定义 | 中-大 | 免费 |
| 贯穿 | 隐私/兜底 | E agent-in-loop | 高价值图会话读图兜底 | 小 | 零新增 |
| P3（可选） | 批量植物检测 | D YOLO | 采集+标注+训练 ONNX | 大 | 免费但费人力 |

**部分特征保存到本地 skill（大哥允许）**：
- **位置**：`assets/game-features/`——模板图（PNG）+ `features.json` 特征定义（名称/类别/识别方法/ROI/相似度阈值）。
- **内容**：植物图标模板、UI 按钮、品质边框、阳光/关卡数字的 ROI 规则、常见错误弹窗模板。
- **好处**：自包含、跟 skill 一起分发、离线可用、模板匹配 ms 级且免费；新植物/新 UI 只需补模板。
- **维护**：游戏版本更新换 UI → 更新模板库（记入 `references/ops.md`）。
- **可选缓存**：已识别图的特征结果按图 URL/hash 缓存到 `data/`，避免重复识别省钱。

**S2 相关性门控怎么做（控费关键）**：
- 启发式先行：正文已长且明确 → 图多为配图；正文短/求助意图 + 带图 → 多为相关。
- 轻量 VLM 二分类兜底（便宜 prompt：「这张图与帖子问题相关吗？相关/无关」）。
- 只有判为「相关」才进 S3/S4 全量识别 → 把 VLM 调用量压到最低。

**S1 取图前置（已实测确认 2026-11-16，详见技术设计稿 §2.1 + evidence/06）**：
- ✅ 图片在 **`moment.topic.footer_images[]`**（非 contents.json），**feed 层即带**，无需额外 detail。
- ✅ 匿名 + **X-UA 头**即可读（非必须登录态）；moment id 用 `id_str`。
- ✅ CDN **无防盗链**，裸 GET `original_url` 即 200 JPEG。
- ✅ 端到端已验证（活动页面样本可下载、VLM 可读）。
- 剩：Node 守护 spawn Python（RapidOCR）的沙盒/stdio 边界 → 推荐本地 HTTP 微服务。

**验收**：
- 码意图帖 100% 跳过图片识别（不误调 VLM）。
- 无关配图按门控跳过；相关图识别内容正确并入 `post.text`。
- 带图求助帖：QA 命中率 / 联网搜到率 / 答疑质量较纯文本有提升（跑样本对比）。
