# 识图调优（传图方式 / 渠道选择 / 任务规格 / JSON 截断）

> 识图 = `skills/image-recognition-ai-ocr`。下面的数字全是本机实测值（2026-11-24~11-25），改参数前先看表，别凭感觉调。

## 场景
守护进程给帖子配图做 OCR / VLM 判定。慢、判错、JSON 解析失败，多数不是模型问题，是**传图方式、渠道顺序、任务规格、token 预算**这四件事没配对。

## 现象
| 现象 | 数字 / 报错 |
|---|---|
| 单张图拖到 100 秒 | 请求体是整张图的 base64：820KB 图 → base64 约 1.1MB，每换一条渠道重传一遍 |
| 判定结果整张图全丢 | `match:img1:unparsable`：JSON 尾部被 `maxTokens` 切掉 → 整体解析失败（实测 3 次丢 2 次） |
| 判定慢 / 渠道全试一遍还是失败 | 提示词没约束「只判断不描述」；没有渠道记忆，失败渠道 10 分钟内又被选中 |
| 视觉渠道只挑到 2~3 条 | 按模型名猜 `vl/omni/vision`，DSH 里 18 个模型实际有 11 个声明了 image 输入 |
| OCR 报错 | `degraded: ['ocr:img1:HTTP 500']`：本地服务没起 |

## 原因
| 现象 | 原因 |
|---|---|
| 100 秒 | 走了 base64 而不是公网 URL，且没先缩图 |
| JSON 截断 | 判定输出是「一个意图一个对象」的数组，撞上限 → 尾巴被切 → **整体**解析失败（其实前几个对象是完整的） |
| 判定慢 / 乱试渠道 | 缺「只判断、不读字、不描述」的提示词约束；缺「上次成功渠道优先 + 失败冷却 + 单次只试 N 条」三件套 |
| 视觉渠道少 | 判据是**模型名**而不是模型**声明的 input 能力** |
| OCR 报错 | `server.py`（8791）没起，或缺 rapidocr / onnxruntime / pillow / numpy / opencv-python |

## 做法
**1. 传图：优先公网 URL**（`vision.preferUrl` 默认开、`vision.shrink` 默认开；没有公网 URL 才回落 base64 且先缩图）
```js
{ type: 'image', url: 'https://cdn.example/a.jpg' }   // ✓ 有公网地址就交给模型自己去取：本地零上传，换渠道不重传
```
实测缩图：**1094KB → 120KB，135ms**（走本地 8791 的 `/resize`，长边默认 1024）。
**2. 渠道记忆**
| 机制 | 默认 | 作用 |
|---|---|---|
| 记住上次成功渠道 | 开 | 下次优先用它，省掉试探 |
| 失败渠道冷却 | **10 分钟** | 冷却期内不重试，别拿大 payload 反复白撞 |
| 单次最多试几条 | **4 条** | **不把 11 条全轮一遍** |
| 按实测延迟排序 | 开 | 快模型先试（EWMA 0.6 新 / 0.4 旧） |
| 无实测时的先验顺序 | flash → mini → small → lite → turbo | 同图 thinking 级模型 50~80 秒，flash 级 3~5 秒 |

调参：`options.vision.maxChannelTries` / `channelCooldownMs` / `debug: true`（打印每条渠道耗时）。
**3. 任务规格（2026-11-25 定，别改）**
| 任务 | 干什么 | 硬约束 |
|---|---|---|
| `match` | 只判断 | 不读字、不描述；依据**一句话 ≤20 字**；**每图只 1 次模型调用**；不注入资料/背景（实测 **1.9~2.7s/图**） |
| `text` | 读字 | OCR 原文**全量、不限字**；OCR 兜底 VLM 预算 **4000 token** |
| `feature` | 认非文字特征 | 描述默认 **≤200 字**；`maxDescChars: 0` = 不限 |

**4. auto 分流（不传 task 时）**：先 OCR（免费）→ 按文字量分流：**≥20 字**当文字图出 `text`，否则当画面图出 `feature` 描述；**auto 与纯 `match` 都不跑 VLM 二分类预筛**（省一次模型调用，纯 match 本身就是判断）。
**5. JSON 被 maxTokens 截断**
- 预算给够：`matchMaxTokens = min(1200, max(320, 140 + 意图数 × 100))`
- 再加一层抢救：常规解析失败就调 `salvageJsonObjects(text)`，把文本里**每一个能完整闭合的对象**单独抠出来解析 → 保住大部分意图，而不是整张图全丢
- 抢救成功记 `degraded: ['match:img1:salvaged']`，并打印 `[判定] <ref> JSON 不完整 → 抢救出 N 条`
**6. 本地服务端口与体检**（服务没起 → `python scripts/server.py`）
| 端口 | 服务 | 接口 |
|---|---|---|
| **8791** | 识图 skill 的 OCR / 模板匹配 / 缩图 | `/health` `/ocr` `/match` `/resize` |
| **8790** | 重排（rerank） | `/health` `/rerank` |

`curl http://127.0.0.1:8791/health` → 应返回 `{"ok":true,"engine":"rapidocr","opencv":true}`；`curl http://127.0.0.1:8790/health` 查重排。
**7. 视觉渠道：按模型声明的 `input` 判定，不猜模型名**（读 `~/.dsh/profiles/*/cordis.patch.yml`）
```yaml
models:
  - id: qwen3.8-max
    input:
      - text
      - image        # ← 有这一行就算视觉模型
```
判据优先级：① 白名单 `visionModels` → ② **DSH 声明的 `input` 含 `image`**（主要依据）→ ③ 名字含 `vl/vision/omni/multimodal`（兜底猜测）。
本机实测：DSH 5 个 provider / 18 个模型里 **11 个**声明了 image 输入，按声明能全挑出来；按名字猜会漏掉其中大部分。查当前渠道：`node -e "import('./scripts/vision.mjs').then(async m=>console.log(await m.resolveVisionChannels({})))"`。

## 检查清单
- [ ] 有公网 URL 的图一律传 URL，不转 base64；走 base64 前先 `/resize`（长边 1024）
- [ ] 失败渠道冷却 10 分钟，单次最多试 4 条，上次成功的渠道排最前
- [ ] `match` 只判断、依据 ≤20 字、每图 1 次调用；`text` 全量不限字；`feature` 默认 ≤200 字
- [ ] auto 与纯 match 都不跑 VLM 二分类预筛
- [ ] 判定用 `matchMaxTokens` 给预算，且保留 `salvageJsonObjects` 兜底
- [ ] `curl http://127.0.0.1:8791/health` 返回 `{"ok":true,"engine":"rapidocr","opencv":true}`
- [ ] 视觉渠道按 `cordis.patch.yml` 的 `input` 含 image 判定，渠道数应在 11 条左右
