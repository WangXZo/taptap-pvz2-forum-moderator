# 写一篇 playbook（经验沉淀规范）

> 这份文档回答：**怎么把一次踩坑/一个做法，写成别人照着就能用的 playbook**。
> 人和 AI 都按这个来 —— 照着写出来的东西，质量应该是一样的。

## 场景

团队里有人踩了个坑、试出个做法，想让别人不再重复踩。口头讲会散，只记在脑子里会忘，
写进 `CHANGELOG` 会淹（那是讲「改了什么」，不是「下次怎么做」）。

`playbook/` 就是放这个的：**按主题组织，不按人** —— 谁踩到谁写，谁需要谁查。

## 现象

不写规范的 playbook 长这样，看着写了其实没用：

| 坏写法 | 为什么没用 |
|---|---|
| 「要注意编码问题，建议统一用 UTF-8」 | 不知道是哪个编码、什么现象、怎么改 |
| 「推送失败时检查网络」 | 真正原因是 TLS 被 RST，检查网络查不出来 |
| 一大段排查过程，结论埋在中间 | 下次遇到的人得读完才能用 |
| 只有结论没有命令 | 懂了但还是得自己摸索怎么敲 |

## 原因

写不具体的两大来源：

1. **凭记忆写** —— 记的是「大概」，漏掉关键数字和具体命令；照着做复现不出来，文档就废了
2. **怕写错** —— 于是改成模糊表述（「可能需要」「视情况」），把不确定性推给读者

正确姿势：**落笔前回仓库核实**（看代码、看当时的报错原文、跑一遍命令），
把「我印象里」换成「L123 这行是这么写的」「报错原文是这句」。

## 做法

### 1. 固定五节结构

每篇必须有这五节，顺序不变：

```markdown
# 主题

## 场景      —— 什么情况下会遇到（限定适用范围，别写成万能）
## 现象      —— 具体症状：报错原文 / 错误码 / 错误表现（表格列几条最快）
## 原因      —— 真正的原因（不是表面症状）
## 做法      —— 具体命令 / 具体改法，能直接复制执行
## 检查清单  —— 写成 - [ ] 勾选项，下次照着过一遍
```

### 2. 三条硬要求

| # | 要求 | 反例 |
|---|---|---|
| 1 | **必须有具体数字** | ❌「很快」→ ✅「1094KB → 120KB，135ms」 |
| 2 | **必须有具体命令** | ❌「重试一下」→ ✅ 给完整可粘贴的命令 |
| 3 | **必须核实过** | ❌ 凭印象 → ✅ 对过代码/报错原文/实跑过 |

**拿不准就写「未核实」，不要写得像核实过。** 这比编一句更像样。

### 3. 每篇 40~80 行，按主题拆

- 太长 → 拆成两篇（读者不是来读小说的）
- 太短（<40 行）→ 说明料不够，先别写，等第二次踩到再补
- 主题粒度：**一个工具链问题 / 一个操作流程 / 一个模块的调优**，不是「所有经验」

### 4. 落笔前自检（机检 + 人检）

```bash
# 结构：五节齐全、代码围栏成对且带语言
grep -c '^## \(场景\|现象\|原因\|做法\|检查清单\)$' playbook/<你的>.md   # 应为 5
grep -c '^```$' playbook/<你的>.md                                        # 应为偶数

# 行数：40~80
wc -l playbook/<你的>.md
```

人检三条：
- [ ] 每节都能独立看懂（不依赖读完全文）
- [ ] 所有命令我**亲手跑过**（或明确标了「未核实」）
- [ ] 没有任何「要谨慎」「注意安全」「视情况而定」这类不产生动作的句子

### 5. 让 AI 帮你写（可选）

可以用子智能体批量起草，但**必须给它这些约束**，否则写出来是空话：

```
在 playbook/ 下写 N 篇中文 Markdown 经验文档。要求：
1. 只创建指定文件，不改其它文件
2. 固定结构：## 场景 → ## 现象 → ## 原因 → ## 做法 → ## 检查清单
3. 中文，简洁，每篇 40~80 行，代码块标语言，命令用 PowerShell/Node 可跑的写法
4. 不要写「要谨慎」「要规范」这类空话；每条要有具体做法、具体命令或具体数字
5. 内容必须对照本仓库真实实现核实后落笔，不许编
6. 写完自检：五节齐全、代码围栏成对、行数区间、关键词覆盖
```

**AI 起草 ≠ 可以跳过核实。** 起草完必须自己过一遍：数字对不对、命令跑不跑得通、
有没有把「可能」写成「就是」。AI 最容易犯的错是把话说满。

> 注：子智能体是宿主（DSH）的运行时能力，**不是本 skill 的资产** ——
> 它不会随仓库分发，别人 clone 下来也不会带着它。随仓库走的只有 `playbook/` 里的成品文档。

## 检查清单

- [ ] 文件在 `playbook/` 下，按主题命名（不是按人）
- [ ] 五节结构齐全，顺序正确
- [ ] 有具体数字（性能/数量/耗时）、有可复制的命令
- [ ] 内容核实过；拿不准的标了「未核实」
- [ ] 40~80 行；超了就拆篇
- [ ] 没有「要谨慎」这类不产生动作的句子
- [ ] 提 PR 前跑过 `grep` 机检（五节齐全 + 代码围栏成对）
