# 介绍 · image-recognition-ai-ocr

> 这份文档回答：它是干什么的、边界在哪、为什么这么设计。

---

## 1. 它解决什么问题

把**图片**变成**可判断的结构化数据**：

```
图片（截图 / 海报 / 表格 / 文档照片 / 游戏画面）
   ↓
结构化结果（文字 / 标签 / 置信度 / 特征 / 分类 / 降级说明）
   ↓
下游自己判断怎么用
```

典型场景：

- 「这张截图里写的是什么？」→ 读字
- 「这几张图，哪张是错误弹窗？」→ 判断（置信度）
- 「这张图里出现了哪些植物、奖励多少？」→ 认特征
- 「这图有没有信息，值不值得继续处理？」→ 判断 + 预筛

## 2. 边界：它做什么，不做什么

| ✅ 属于本 skill | ❌ 归下游 |
|---|---|
| 取图（通用字段 + 可注入提取器） | 业务意图判定（该不该回、要不要跳过） |
| 图片质量预筛（无图/过小/重复） | 回复文案生成、语气、话术 |
| 通用相关性判断（这图有没有信息） | 业务相关性（这图对某个具体回答有没有用） |
| 三通道识别：模板 / OCR / VLM | 是否采纳结果、置信度阈值定多少 |
| 通用标签与分类（含中文/含数字/场景类型） | 业务分类（某游戏的活动页/图鉴/报错） |
| 结构化输出 | 曝光策略、成本控制 |

**为什么要把业务判断推给下游**：
同一张图，在「论坛答疑」里和在「客服工单」里，该不该处理、怎么处理完全不同。
识图侧如果自己决定，就把判断权锁死了；给结构化结果 + 置信度，下游能自己定阈值。

**为什么「这图值不值得识别」留在本 skill**：
那是**成本问题**（VLM 按图计费），不是业务问题。挡在识别之前，所有调用方都受益。

## 3. 为什么是「任务驱动」而不是「流水线」

早期设计是固定流水线（取图 → 门控 → 识别 → 回灌）。问题在于：

- 调用方只想读字，却被迫跑一遍模板匹配
- 想做判断，却拿不到置信度，只有一段文字
- 业务门控塞在流水线里，换场景就得改识图代码

现在的模型是：**你说要什么，我给什么**；你没说，我自己按图判断。

```
task: 'match'   → 你要判断，我给置信度（一句话，最省时间）
task: 'text'    → 你要文字，我给全量文字 + 标签
task: 'feature' → 你要特征，我给特征 + 描述
tasks: [...]    → 你都要，我一次跑完（共享取图/下载/缓存）
（不传）        → auto：按图片内容自己判断该读字还是该描述
```

### 3.1 为什么要有 auto

调用方经常**判断不出**「这张图是截图还是画面」：

- 判断错了会浪费——把游戏画面当截图去读字，读到空，还白等了模型
- 让调用方先探测一遍再决定，等于把成本转嫁给调用方，而且它也没有更好的信息

所以默认交给本 skill：先 OCR（免费、本地），**文字量本身就是最好的判据** ——
有字就是文字图，没字就是画面图。调用方只给图，拿到结果。

显式传 `task` 时自动分流不介入 —— 调用方明确知道自己要什么时，内部规则不该多嘴。

## 4. 三通道的取舍

| 通道 | 为什么用它 | 为什么不用它 |
|---|---|---|
| **模板匹配** | 已知特征免费、精确、可复现、离线 | 只认见过的；换 UI 就失效 |
| **OCR** | 读字准、免费、离线 | 只出字不理解；画面乱就读不出 |
| **VLM** | 开放语义、能判断、能描述 | 按图计费；会臆造、数字易错 |

顺序恒为 **模板 → OCR → VLM**（先便宜后贵）。任一条不可用就跳过它，不阻断其它。

## 5. 资料层的设计理念

本 skill **可以有自己的资料**，不只用调用方给的。三层：

| 层 | 谁写的 | 放什么 |
|---|---|---|
| `builtin` | 本 skill 作者 | **通用**知识：场景分类法、标签词表 —— 放哪都成立 |
| `caller` | 调用方 | **具体项目**：这是什么游戏、术语表、示例 |
| `learned` | 运行时沉淀 | 人工确认过的新标签/新说明，下次自动带上 |

合并优先级：`builtin` → `caller` → `learned`（后者覆盖前者，按 id）。

**为什么业务资料不放内置层**：
内置层如果塞进某个游戏的植物图鉴，这个 skill 就不通用了。
所以内置层只放「通用知识」，业务专属的一律由调用方传。

`context`（一句话背景）和 `materials`（结构化资料）都拼进 prompt，帮模型判断更准。

## 6. 预筛：省钱的第一道闸

```
① 质量预筛（免费）
   无图 / 下载失败 / 体积过小 / 本批重复 → 跳过
② VLM 二分类（一次小调用）
   问「这图有信息吗」，答「无」→ 跳过后续所有识别
```

两层都可关。**判不准时保留** —— 宁可多识别，不漏信息。

② 与「每图时间最短」冲突，所以 **auto 与纯 `match` 一律跳过它**：
auto 已经用 OCR 文字量做了分流，纯判断本身就是在判断这张图值不值得看。
显式要 `text`/`feature` 时才按配置跑。

被挡下的图会写在 `meta.skipped` 里，带原因，不静默；结果行也保留一条（`skipped` 字段），下游能对上号。

## 7. 失败语义：降级，不抛错

| 情况 | 行为 |
|---|---|
| 看图渠道没配 | VLM 相关跳过，`degraded: ['vlm:no-channel']` |
| OCR 服务没起 | OCR 跳过，`degraded: ['ocr:img1:HTTP 500']` |
| 没传模板 | 模板通道跳过，`degraded: ['template:no-templates']` |
| 模型没按 JSON 回 | 该图结果跳过，`degraded: ['match:img1:unparsable']` |
| 参数非法（缺 images / 未知任务） | 唯一的 `ok:false` 场景 |

**没装本地服务、没配 VLM 也能跑** —— 只是拿到的结果少一些，调用方看 `degraded` 就知道缺什么。

## 8. 谁在用

- `taptap-pvz2-forum-moderator`（植物大战僵尸2 论坛版主 skill）：
  自己做业务门控（求码帖不读图）、注入 PVZ2 看图 prompt、传入自己的模板库，
  调本 skill 的 `recognize({tasks:['text','feature']})`，再把结果回灌到帖子正文。
  它把本 skill 当作**独立 skill**引用 —— 两边可各自独立安装与使用。
